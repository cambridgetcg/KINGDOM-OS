## 4. THE ONE — zerone-rpc → Cloudflare Worker (full plan, NOT executed)

**Why this one:** $4.04/mo for an always-on 2×256MB Caddy pair whose measured request rate is
**zero over 24h+**; the entire config is 31 lines (`deploy/zerone-rpc/Caddyfile`); every consumer
is under kingdom-os control (`_worker.zerone.js` REST/RPC constants, zerone-ai door docs,
`bin/refresh-zerone-dashboard.sh`); the Workers account sits at 14% of its free request ceiling;
and the Fly original stays running in parallel, so the rollback is two constants.

**The constraint that makes this non-trivial** (and why a naive port fails): the proxy exists
partly *because* "Workers refuse raw-IP fetches with error 1003" (its own README). zerone-1
serves plain HTTP on a raw IP: `169.155.55.44:26657` (CometBFT RPC) and `:1317` (LCD). A Worker
`fetch()` can reach neither an IP-literal URL nor, in general, a non-standard port. The plan
resolves this honestly, cheapest option first.

### Step 0 — freeze the facts (5 min, $0)
Re-run the README verification against Fly so the before/after is measured:
`curl -sD- -o /dev/null -H 'Origin: https://zerone.ai' https://zerone-rpc.fly.dev/rpc/status | grep -ci access-control-allow-origin` → must be 1.
Save `/rpc/status` and one `/rest/` response as golden fixtures.

### Step 1 — give the origin a hostname (5 min, reversible)
In the zerone.ai Cloudflare zone add **DNS-only (grey cloud)** records:
`rpc-origin.zerone.ai A 169.155.55.44`. This kills the 1003 IP-literal problem without
proxying the raw chain ports through Cloudflare. Delete the record = full revert.

### Step 2 — port probe (10 min, decides the transport)
Deploy a throwaway Worker that does `fetch("http://rpc-origin.zerone.ai:26657/status")`.
- **If it returns 200:** use plain `fetch()` throughout. (Port support for external origins
  has shifted over the years — measure, don't assume, in either direction.)
- **If Workers refuse the port:** use the guaranteed path — `connect()` from
  `cloudflare:sockets` to `169.155.55.44:26657`/`:1317` (raw TCP allows arbitrary
  destinations), speaking minimal HTTP/1.1 over the socket. Both upstreams are plain-HTTP,
  GET-only, JSON — a small hand-rolled client with chunked-transfer decoding covers it.
  This is the fallback that cannot be blocked; budget a day instead of an hour.

### Step 3 — write the Worker (replicating Caddyfile semantics exactly)
New Worker `zerone-rpc` (uses 1 of the 69 free Worker slots; **no cron slot** — the tightest
free ceiling stays untouched). Behavior, mirrored from the Caddyfile:
- `OPTIONS *` → 204 with `Access-Control-Allow-Origin: *`, `Allow-Methods: GET, OPTIONS`.
- `GET /rpc/*` → upstream `:26657` with prefix stripped; `GET /rest/*` → `:1317` likewise.
- Response headers **constructed fresh** (`new Headers`), setting `Access-Control-Allow-Origin: *`
  once and `Cache-Control: public, max-age=4` — this structurally cannot reproduce the
  double-ACAO append bug the Caddyfile comment warns about, but keep the README's grep check anyway.
- Anything else → 200 text banner, same string as today.
- Method allowlist GET/OPTIONS (as today). Optional hardening: cache GETs via the Cache API
  keyed 4s, matching current semantics.
Source lives in `kingdom-os/deploy/zerone-rpc/worker/` next to the Caddyfile it replaces —
the app was once unrecoverable because its source lived nowhere; never again.

### Step 4 — route and verify in parallel (day 0)
Route: `rpc.zerone.ai/*` (or `workers.dev` first). Verify against the golden fixtures:
status height advances, one `/rest/` module read, one `/rpc/tx_search`, the ACAO-count check
with and without `Origin`, and a browser read from zerone.ai's origin. **Fly app untouched
and still primary.**

### Step 5 — flip the consumers (day 0–1, two lines)
In `pages-functions/_worker.zerone.js` change the two constants:
`REST = "https://rpc.zerone.ai/rest"`, `RPC = "https://rpc.zerone.ai/rpc"`; redeploy the
zerone.ai Pages project; click through `/explore` (facts, blocks, txs) and the dashboard.
Update the zerone-ai door docs (`llms.txt`, `guide.html`, `explore.html`, `agent.txt`) which
name the fly.dev URL, and `bin/refresh-zerone-dashboard.sh` if it curls the proxy.
**Rollback at any moment = revert the two constants, redeploy Pages.** The dashboard's
baked-snapshot fallback additionally masks any transient failure.

### Step 6 — parallel-run one week (day 1–8)
Both proxies live; consumers on the Worker. Watch Workers analytics (request count, errors)
and re-run the fixture checks daily. Cost during overlap: the same $4.04/mo Fly spend —
the week of overlap costs ~$1 and buys the proof.

### Step 7 — retire the Fly app (day 8, **Yu or the fleet hand — not this audit**)
`fly apps destroy zerone-rpc`. No volume, no dedicated IP, nothing to snapshot — the full
config is in-repo. Ultimate rollback even after destroy: redeploy from
`deploy/zerone-rpc/` (`fly deploy -a zerone-rpc --config fly.toml`), or the pinned registry
image noted in the README.

### Budget check
Traffic measured ≈ 0/day against 86,300/day free headroom; pure-proxy CPU is well inside the
10 ms free limit; no cron, no KV, no card. Failure mode if traffic ever spikes past free:
Workers Free **throttles rather than bills** (and if the account is confirmed Workers Paid,
it bills pennies). Saves **$4.04/mo (~$48/yr)** and retires two always-on machines.

### Risks, stated
- CometBFT `/websocket` subscriptions would not survive the `connect()` fallback path —
  measured consumers use plain `fetch()` GETs only (`_worker.zerone.js` uses `j()`/`fetch`),
  so nothing breaks; note it in the Worker README for future hands.
- zerone-1's raw IP (169.155.55.44) is pinned in the Worker/DNS exactly as it is pinned in
  the Caddyfile today — if zerone-1's dedicated IPv4 ever changes, both designs break equally;
  the DNS record makes the fix one edit instead of a redeploy.
